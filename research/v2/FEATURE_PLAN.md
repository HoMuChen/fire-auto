# 找新特徵的規劃（交接用，2026-11-03 擬定，尚未開始）

這份是給下一位接手的 agent 的工作計畫。**階段 0～3 已完成（第四十三批 FL2、第四十四批 FS6、第四十五批 FS7、階段 3 對照表 `FACTOR_MAP.md`）**。第四十六、四十七、五十六、五十七批 FS8～FS11 已從 `FACTOR_MAP.md` 挑 69 個跑完；剩下的 29 個在第五十七批登記時歸類為已測變體或做不到，**對照表已經沒有「現有資料可做」的因子**，之後要找新特徵得找新資料或新來源。要從哪個階段開始，由使用者決定；開始前先跟使用者確認。

## 先讀

1. 根目錄 `AGENTS.md`「研究規範」：期間、事前登記、防前視、成本。
2. `research/v2/FEATURES.md`：目前的特徵庫，68 個特徵。檔案由程式產生，不要手改。
3. `research/v2/HYPOTHESES.md` 的第四十一批（FL1 規則）和第四十二批（FS5，最近一批）：評估方法和最新結果。
4. `research/v2/README.md` 的檔案表：每支程式在做什麼。

## 現況

- 特徵庫目前 163 個特徵（月報酬 A＋B）：收 66、未收 16、資料不足 77、待確認 4；資料不足的改走 B＋V（見 FEATURES.md 文末）。
- 最可靠的標籤是 `◎✓✓`，安慰劑假陽性 0%；一般「收」的安慰劑比例是 25%，所以 61 個「收」裡大約有 15 個可能是假的。
- **使用者的原則**：特徵只看自己夠不夠好，按用途貼標籤，留著以後重複用。**不以「能不能改進 H136」或「適不適合每月 20 檔」當門檻**；H136 增量只是描述用的欄位。
- 實盤策略：H136，`h2_monthly.py` 在 ai-dev 上執行。研究不要動它。

## 規則（違反任何一條都要先問使用者）

- **事前登記**：每一批在跑之前，先把特徵定義、參數和判定方式寫進 `HYPOTHESES.md`。
  - 批次編號：下一批應該是第四十八批。另一個 session 也會直接在 main 上 commit，所以開始前要先看 `HYPOTHESES.md` 的結尾確認編號。
- **評估**：照 FL1 引擎（`feature_library.py`）。
  - 方向用 A 段（2010–14）IC 的正負號決定。
  - dev 的 A、B 兩段（B 是 2015–19）給標籤，val（2020–23）確認，另外跑安慰劑。
  - 新特徵加進 `FEATS` 後重跑。**原本 68 個特徵的數字、標籤、狀態必須完全不變**，跑完後和前一版 `data/v2/results/feature_library.csv` 逐欄比對。
- **holdout（2024 以後）不開**，除非使用者明確同意，而且只能看一次。
  - 已經用過 holdout 的：H131、H136、H137。
  - M2（ML1 的 HistGB 模型）的 holdout 已經看過，不要再拿 M2 的混合去測 holdout。
- **公開 repo**：fire-auto 在 GitHub 是公開的，FinMind 資料僅限個人使用。repo 裡只能寫統計量，不能寫原始數字。`data/` 已經 gitignore。
- **FinMind 額度**：上限每小時 6,000 次，和 ai-dev 的實盤排程共用。**任何新的 API 呼叫都要先問使用者。**
  - ai-dev 的排程：18:00 stock_cache；18:30／18:35 期貨；20:30 h2_monthly；22:00 broker_cache（約 1 小時、1,400 次）；00:30 lake daily；08:01 總經；08:40 訂單簿；09:15–13:45 期貨監控。
  - 抓法：`fetch_fundamentals.py --rate 30 --quiet`，每分鐘 30 次。`--quiet` 會暫停在 17:55–18:50、20:25–21:00、21:55–23:15、00:25–01:00 這四段，也就是會打 FinMind 的那幾個排程。
- **套件**：研究用的套件用 `uv pip install`，**不要用 `uv add`／`uv lock`**。uv.lock 鎖的 shioaji 1.7.2 已經從 PyPI 下架，重新 lock 會改動實盤依賴。
- **git**：只有使用者要求時才 commit 或 push。先開分支，commit 完切回 main。不要 commit 不是你改的檔，也就是使用者自己還沒提交的 WIP。
